## What this was

A client engagement at Oncloud. The organization was running a perimeter-based model that hadn't kept up with their shift to remote work — unmanaged personal devices accessing corporate data, weak auth, no consistent security baseline across Windows, macOS, and mobile.

The goal: every device accessing M365 should be known, enrolled, compliant, and continuously verified.

## What I did

**Intune security baselines** — deployed Microsoft's baselines as a starting point, then layered custom CSPs for BitLocker enforcement and EDR sensor requirements. Built a compliance engine that automatically blocks M365 access for non-compliant devices.

**Conditional Access redesign** — audited the existing CA policies (there weren't many good ones), rebuilt from scratch. Enforced phishing-resistant MFA (FIDO2) and required a compliant device signal before accessing sensitive workloads. Took several iterations to get right without locking people out.

**Defender for Endpoint onboarding** — automated EDR onboarding across 10,000+ endpoints via Intune. Tuned alert configuration to reduce noise before handoff.

**Hardware attestation** — enforced TPM-based attestation and Secure Boot across the Windows fleet. Trickier with mixed hardware generations than it sounds.

**Exchange Online and MAM** — tightened mail-flow rules and deployed Mobile Application Management policies so corporate data couldn't leave via personal apps on unmanaged phones.

## What made it hard

Conditional Access is easy to get wrong in both directions. The first FIDO2 rollout broke access for users on older hardware that didn't support it. We ran a grace period with fallback MFA while hardware was replaced — unplanned but necessary.

- Microsoft Intune
- Microsoft Entra ID
- Defender for Endpoint (XDR)
- PowerShell & Microsoft Graph API

## What this is

A collection of production n8n workflows I've built and iterated on for client work at Oncloud. Not a demo library — these run on actual client environments and handle real operational tasks.

## What's in it

**Security incident enrichment** — when a Sentinel alert fires, automatically pull context from VirusTotal, AbuseIPDB, and Entra ID risk scores. The analyst gets a pre-enriched package instead of starting from scratch on every alert. Cuts the "what is this IP?" lookup step out of triage entirely.

**Identity lifecycle** — listens to HR events from HiBob (new hire, termination, role change) and triggers the corresponding Entra ID actions automatically. Provisioning, deprovisioning, group membership changes — all handled without an IT ticket.

**License auditing** — scans for unassigned M365 licenses and dormant user accounts on a schedule, generates a report, and creates remediation tasks. The kind of thing that saves money but never gets done manually because it's tedious.

**Incident notification routing** — routes alerts to the right channel (Teams, Slack, email, PagerDuty) based on severity and type. Sounds simple, but getting the routing logic right for different client environments required more iteration than expected.

## What I learned building these

n8n is genuinely good for this kind of work but error handling in production requires discipline. If a workflow fails silently at 3am because an API returned an unexpected shape, you don't find out until someone asks why something didn't happen. Every critical workflow now has explicit error branches and failure notifications.

- n8n (self-hosted)
- Azure Logic Apps (for some client environments)
- Microsoft Graph API
- Microsoft Sentinel
- HiBob, VirusTotal, AbuseIPDB APIs

## What this is

A companion to FleetWatch, built for analytical depth rather than day-to-day fleet operations. Where FleetWatch is fast search and direct device actions, this is compliance trend analysis, cross-fleet aggregations, and audit reporting.

Built for environments where the data volume makes native Intune reporting impractical.

## Why OpenSearch

At 50,000+ devices with hundreds of properties each, the queries that matter for security auditing — "show me all Windows 10 devices with BitLocker disabled, sorted by last sync time, filtered by region" — are aggregation queries that relational databases handle poorly at this scale. OpenSearch handles them well and the full-text search is a side benefit.

## What it does

**Elastic search across the fleet** — complex boolean queries on device state. Find devices by any combination of properties in milliseconds.

**Compliance heatmaps** — visualize non-compliant devices by location, department, or OS version. Useful for spotting systemic issues rather than individual device problems.

**Trend analysis** — compliance over time per policy. Shows whether a remediation effort actually worked, or whether drift is recurring.

**Audit exports** — CSV/PDF compliance reports for regulatory requirements. The kind of thing that used to take someone a day to compile manually.

## How data stays current

Node.js workers run continuous sync from Microsoft Graph, pulling device state and pushing updates to OpenSearch. The data is fresh enough for security auditing purposes without hammering the Graph API rate limits.

- Next.js
- OpenSearch (AWS Managed)

Intune Autopatch automates Windows, Microsoft 365 Apps, Edge, and Teams updates to improve security and productivity. To ensure patches are correctly applied and systems remain compliant, organizations can use Intune Proactive Remediations to detect missing patches and remediate them automatically. This guide provides a verifiable, end-to-end flow for engineers to implement and validate automated patching.

## Introduction

Automated patching reduces administrative overhead and improves security posture by ensuring timely updates. Windows Autopatch manages update rings and cadence as a service, while Intune Proactive Remediations allow custom detection and remediation scripts to verify patch state and fix issues automatically.

## Prerequisites

- Licensing: Microsoft 365 Business Premium, Windows 10/11 Education A3/A5, Windows 10/11 Enterprise E3/E5 (including F3), or VDA equivalents.
- Device platform: Windows 10/11 Enterprise/Education, Windows IoT Enterprise (certain LTSC limitations apply).
- Network: Internet access to Intune, Windows Update, and Autopatch endpoints.

## Step 1: Verify Prerequisites

Confirm licenses are assigned to users or devices. Ensure devices run supported Windows editions. Validate network connectivity to required endpoints (*.manage.microsoft.com, *.update.microsoft.com, etc.).

## Step 2: Enroll Devices in Windows Autopatch

In the Microsoft Endpoint Manager admin center:
1. Navigate to Devices > Windows > Windows Autopatch > Enroll.
2. Select device groups (Entra groups) to enroll.
3. Confirm enrollment status in the Autopatch enrollment blade.

## Step 3: Configure Update Rings (if needed)

Autopatch creates default Test and Last rings. Review them via Intune > Devices > Update rings.
- Avoid assigning custom rings to Autopatch-managed devices; rely on service-managed policies.
- Adjust ring settings (deferral, grace periods) only for opt-out groups.

## Step 4: Deploy Proactive Remediation Script for Patch Verification

Create a detection script that checks for the latest quality update KB (returns exit code 0 if compliant, non-zero if action needed). Create a remediation script that triggers Windows Update or resets Windows Update components.

Example detection script (PowerShell):
```powershell
# Check for KB500xxxx (example)
$hotfix = Get-HotFix -ID KB500xxxx -ErrorAction SilentlyContinue
if ($hotfix) { exit 0 } else { exit 1 }
```

Example remediation script (PowerShell):
```powershell
# Trigger Windows Update scan and install
usoclient StartScan
usoclient StartInstall
# Alternatively, reset Windows Update components
net stop wuauserv
net stop cryptSvc
net stop bits
net stop msiserver
ren C:\Windows\SoftwareDistribution SoftwareDistribution.old
ren C:\Windows\System32\catroot2 catroot2.old
net start wuauserv
net start cryptSvc
net start bits
net start msiserver
```

Deployment steps in Intune:
1. Upload detection and remediation scripts as a script package (Intune > Devices > Scripts).
2. Assign to targeting groups (can be the same Autopatch group or Entra group).
3. Set schedule (e.g., every 8 hours) and user context (System).
4. Enable notifications for failed detections.

## Step 5: Monitor Compliance and Alerts

Monitor sources:
- Intune device compliance and update compliance reports.
- Windows Autopatch Management Status Report (tenant-wide view of eligible devices).
- Windows Autopatch Alert Report (active alerts, severity, impacted update types).

Validation checks:
- Detection scripts run on schedule to verify patch state.
- Manual verification via Get-HotFix, Get-ItemProperty for registry keys, or WSUS/ConfigMgr queries.
- Handling failed patches:
  - Detection failure triggers remediation script (e.g., retry Windows Update, reset Windows Update components).
  - If remediation fails, device marked non-compliant; admin can investigate logs (WindowsUpdate.log, SetupAPI.log).
  - Rollback options: Use Windows Update for Business uninstall policies, or deploy a script to uninstall the problematic update via wusa.exe /uninstall.
- Reporting and alerting:
  - Configure alert rules in Intune for compliance drift.
  - Use Autopatch alert email notifications or webhook integrations.
  - Export reports to Power BI or Log Analytics for trend analysis.

## Step 6: Remediate Failures and Verify Fixes

- When detection fails, remediation script runs automatically.
- Verify success by checking subsequent detection returns exit code 0.
- If persistent failure, open ticket, collect logs, consider pausing the update ring for that device group.

## Step 7: Review Reports and Adjust Policies

- Weekly: Examine Intune update compliance trends.
- Monthly: Review Autopatch reports for rollback/pause events.
- Adjust ring deferrals or exclusion groups based on observed issues.
- Update detection/remediation scripts as new KBs are released.
