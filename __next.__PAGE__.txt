MediaFusion solves a critical challenge in the streaming ecosystem: how to securely authenticate users on devices with limited input capabilities. From Stremio addons on Android TV boxes to Kodi installations on Raspberry Pis, many streaming devices lack full keyboards or browsers, making traditional OAuth flows impractical. MediaFusion addresses this by implementing the OAuth 2.0 Device Authorization Grant (RFC 8628), creating a seamless authentication experience that never requires users to enter credentials on the device itself.

## What is MediaFusion?

MediaFusion is an open-source streaming platform that aggregates content from configured sources—including torrent indexers, debrid services like RealDebrid and Premiumize, metadata providers, and enhancement services—into a unified interface accessible through Stremio, Kodi, or directly in a browser. Acting as an aggregation layer, it connects to over 40 external services across six major categories, eliminating the need to juggle multiple apps or websites.

The platform's strength lies in its ability to present a unified streaming experience while handling the complexity of authentication with various backend services behind the scenes.

## The OAuth 2.0 Device Authorization Grant Explained

The OAuth 2.0 Device Authorization Grant (also known as "device flow") is specifically designed for input-constrained or browserless devices. Unlike traditional OAuth flows that require redirects or embedded browsers, device flow enables authorization through a secondary device like a smartphone or laptop.

Here's how MediaFusion implements this flow:

1. **Device Authorization Request**: When configuring a debrid service (like RealDebrid), MediaFusion's configuration UI makes a GET request to the provider's `/provider/device_code` endpoint to obtain a device code and user code.

2. **User Code Display**: The configuration interface displays the user code and instructs the user to visit a verification URL on a separate device (typically a smartphone or computer) with full input capabilities.

3. **User Authorization**: The user visits the verification URL on their secondary device, enters the user code, and grants authorization to MediaFusion.

4. **Polling for Token**: While the user authorizes, MediaFusion polls the token endpoint (`/provider/authorize`) with the device code at intervals specified by the provider (typically every 5 seconds) until authorization completes or the code expires.

5. **Token Reception**: Upon successful authorization, the token endpoint returns an access token, which MediaFusion encrypts and embeds in the manifest URL via the `secret_str` parameter for seamless addon configuration.

## Why Device Flow Provides Excellent UX for MediaFusion Users

The device flow solves the authentication dilemma for streaming addons in several key ways:

- **No Browser Required on Device**: MediaFusion runs on devices that may lack browsers or have limited input (like TV boxes or Raspberry Pi setups). The device flow eliminates the need for browser-based authentication flows on these constrained devices.

- **Secondary Device Authentication**: Users complete authorization on familiar devices with full keyboards and browsers—typically smartphones or laptops—making the process intuitive and error-free.

- **Simple Code Entry**: Instead of entering complex credentials, users only need to input a short, alphanumeric user code (typically 6-8 characters), reducing friction and errors.

- **Automatic Polling**: After displaying the user code, MediaFusion automatically handles the polling process in the background, requiring no further user interaction until authorization completes or times out.

- **URL-Based Configuration**: Encrypted credentials are embedded directly in the manifest URL, eliminating separate login steps when installing the Stremio or Kodi addon. Users simply install the addon with the pre-configured manifest URL, and it just works.

## Security Analysis: What Device Flow Protects Against

The device flow provides inherent security benefits by design:

### What It Protects Against
- **Credential Exposure**: User credentials (username/password) never enter the MediaFusion device interface, eliminating credential theft from compromised devices.
- **Limited Attack Surface**: Only the device code and user code are exposed on the limited-interface device, minimizing the attack surface.

### Security Considerations & Mitigations
While inherently more secure than alternatives like Resource Owner Password Credentials (ROPC), device flow requires attention to several considerations:

1. **User Code Brute Forcing**: RFC 8628 §5.1 specifies that user codes must be sufficiently long and random to prevent brute-force attacks. MediaFusion relies on provider-standard implementations that typically use 8-character alphanumeric codes (62^8 ≈ 218 trillion possibilities).

2. **Device Code Brute Forcing**: Similarly, device codes must be sufficiently entropic (RFC 8628 §5.2). Providers implement these with sufficient entropy to make brute-forcing impractical.

3. **Phishing Risks**: Users must verify they're entering codes on legitimate provider verification pages. MediaFusion mitigates this by displaying the exact verification URL to visit.

4. **Polling Abuse**: Providers must implement rate limiting on token endpoints to prevent abuse from frequent polling—a standard requirement RFC 8628 §5.4 places on authorization servers.

5. **Token Lifetime Management**: Access tokens should have appropriate expiration times, with refresh token support where applicable, limiting the window of compromise if tokens are intercepted.

6. **PKCE Considerations**: While RFC 8628 doesn't mandate PKCE for device flow, some providers implement it additionally. MediaFusion works with provider implementations as-is.

## Device Flow vs. Alternative OAuth Flows

Understanding when device flow is the right choice requires comparing it to other OAuth flows:

### Device Flow vs. Authorization Code + PKCE
- **Device Flow**: Designed for input-constrained/browserless devices; uses user code + verification URL; client polls for token
- **Auth Code + PKCE**: Requires browser/user-agent on device; uses redirect_uri; authorization server redirects back to client

### Device Flow vs. ROPC (Resource Owner Password Credentials)
- **Device Flow**: Never handles user credentials; more secure against credential theft and phishing
- **ROPC**: Requires username/password handled by client; vulnerable to phishing, keylogging, and credential theft

### When Device Flow is Appropriate
Device flow is ideal when:
- Devices lack browsers or have limited input capabilities (smart TVs, streaming sticks, gaming consoles)
- You want to avoid handling user credentials on the device
- Users have access to a secondary device for authorization
- Deploying streaming/media addons (Stremio/Kodi) where seamless configuration is paramount

## How MediaFusion Implements Device Flow Technically

Based on source code analysis, MediaFusion's implementation follows these patterns:

### Device Code Request
The configuration UI initiates the flow by calling `GET /{provider}/device_code` (found in `resources/js/config_script.js` lines 33-60), which returns:
- `device_code`: Used for polling the token endpoint
- `user_code`: The code users enter on the verification page
- `verification_uri`: The URL users should visit
- `expires_in`: Validity period (typically 5-15 minutes)
- `interval`: Polling interval in seconds (usually 5)

### Token Polling
While the user authorizes, MediaFusion POSTs to `/{provider}/authorize` with the `device_code` (lines 63-96 in config_script.js), respecting the provider-specified interval to avoid abuse.

### User Code Display
The configuration interface (`resources/html/configure.html` lines 235-242) presents the user code and instructions clearly, often with copy-to-clipboard functionality for ease of use.

### Token Storage
Upon receiving the access token, MediaFusion:
1. Encrypts it using AES via `utils/crypto.py` with a site-specific `settings.secret_key`
2. Embeds the encrypted token in the manifest URL as the `secret_str` parameter
3. This allows Stremio/Kodi addons to load configured services without additional login steps

The encryption implementation spans `utils/crypto.py` and `db/schemas.py` (lines 235-348), ensuring credentials never remain in plaintext in configurations or URLs.

## Best Practices for Users When Authorizing Devices

To maximize security when using MediaFusion's device flow:

1. **Verify the Verification URL**: Always ensure you're on the legitimate provider's website when entering user codes.
2. **Use Temporary Codes**: Treat user codes as temporary passwords—don't share them or enter them on suspicious sites.
3. **Monitor Authorized Devices**: Regularly review and revoke access for devices you no longer use via the provider's account dashboard.
4. **Understand Token Scope**: Be aware of what permissions you're granting (typically limited to accessing your debrid/storage account).
5. **Keep Recovery Options Updated**: Ensure account recovery methods are current in case you need to regain access.

## Why This Approach Represents the Future of Device Authentication

MediaFusion's implementation of OAuth 2.0 Device Flow exemplifies a broader shift in how we handle authentication for the growing ecosystem of smart devices, IoT gadgets, and media-centric hardware:

- **User-Centric Security**: By separating authentication from the device interface, we achieve both security and usability without compromise.
- **Standardized Approach**: Leveraging RFC 8628 ensures compatibility with major identity providers while benefiting from community-vetted security practices.
- **Seamless Integration**: The URL-based credential embedding creates a truly "set it and forget it" experience for addon installation and configuration.
- **Extensible Framework**: As more services adopt device flow (from Google to Azure AD), MediaFusion's modular implementation can easily integrate new providers.

For streaming enthusiasts who value both convenience and security, MediaFusion's device flow implementation demonstrates how thoughtful authentication design can make complex backend integrations disappear behind a simple, "just works" user experience—exactly what the modern streaming ecosystem needs.

# Securing AI Agents: Threat Model and Guardrails for Production

AI agents—LLMs augmented with tool use, memory, and planning—are now deployed in production clouds. They introduce risks beyond classic prompt injection, including tool abuse, data exfiltration, and privilege escalation. This article provides a zero‑trust playbook for securing AI agents at scale, grounded in recent academic surveys, real‑world case studies, and industry cheat‑sheets.

## Core Threat Model for AI Agents

### Prompt Injection / Tool Manipulation
Attacker‑controlled input causing unwanted tool calls or data leaks.  
*Citations: [1,2,4,5]*

### Data Exfiltration & Lateral Movement
Agents with excessive permissions read/exfiltrate data or pivot to other services.  
*Citations: [1,2]*

### Over‑Privileged Agent Identities
Excessive IAM roles/service accounts enable privilege escalation.  
*Citations: [1,2]*

### Indirect / Second‑Order Injection
Malicious data returned by tools corrupts the agent’s reasoning.  
*Citations: [3,6]*

### Runtime & Supply‑Chain Risks
Compromised tool images, unsafe plugins, credential leakage.  
*Citations: [2,3]*

*Sources:*

[2] Astrix guide  
[3] ClawGuard runtime security framework

[5] Astrix guide

## Least‑Privilege / Capability‑Based Access Control (ABA)

### Per‑Agent Credentials & Short‑Lived Tokens
Use workload identity (OIDC federation, Azure/Google workload identity) so agents never store long‑lived secrets.  
*Citations: [2,6]*

### Scoped Tool Access
Each agent gets a minimal allowlist of APIs/commands, enforced via sidecar proxies or API gateways.  
*Citations: [2,6]*

### Runtime Policy Engines
e.g., Open Policy Agent (OPA) or Kubernetes PSP/OPA‑Gatekeeper to deny privileged syscalls.  
*Citations: [2]*

*Source:* “Caging the Agents” – credential proxy sidecars prevent containers from accessing raw secrets.

## Securing the Agent Runtime & Deployment

### Workload Isolation
Use gVisor, Kata Containers, or lightweight VMs to sandbox agent processes.  
*Citations: [6]*

### Network Egress Controls
Allow‑list destinations per agent (e.g., Kubernetes NetworkPolicy, AWS Security Groups, Azure NSG).  
*Citations: [6]*

### Secret Management
Inject secrets via sidecar or CSI driver; never mount directly into agent filesystem.  
*Citations: [2,6]*

### Audit Logging & Tamper‑Evident Trails
Log every tool call, LLM prompt/output, and credential access; ship to SIEM/chronicle.  
*Citations: [2,6]*

### Human‑in‑the‑Loop / Approval Gates
Require approval for destructive actions (e.g., `kubectl delete`, `aws s3 rm`).  
*Citations: [2,6]*

*Sources:*  
- “Caging the Agents” – four‑layer defense: gVisor isolation, credential sidecar, network egress allowlist, prompt‑integrity framework  
- “Towards trustworthy agentic AI” – discusses isolation, secrets, logging, approval mechanisms

## Identity & Trust Boundaries

### Workload Identity Federation
Agents authenticate to downstream APIs using short‑lived JWTs from Azure AD Workload Identity, Google Workload Identity Federation, or AWS IAM Roles for Service Accounts (IRSA).  
*Citations: [2]*

### Mutual TLS / SPIFFE
Establish service‑to‑service trust between agents and backend APIs.  
*Citations: [2]*

### Tool/Plugin Signing & Attestation
Verify code signatures before loading plugins.  
*Citations: [2,3]*

*Source:* “Towards trustworthy agentic AI” – covers OIDC federation and workload identity.

## Practical Guardrails an Infra/Security Engineer Can Implement Today

### Prompt‑Integrity Framework
Wrap untrusted tool outputs in structured metadata (e.g., JSON with `trusted: false`) and apply validation/sanitization before feeding back to the LLM.  
*Citations: [6]*

### Input Sanitization & Allow‑Listing
Reject prompts containing known injection patterns (e.g., `<<SYS>>`, `[[[`, `]]]`).  
*Citations: [4,5]*

### Output Encoding / Sandboxed Execution
Run tool‑generated code in a sandbox (gVisor, Firecracker) and enforce SELinux/AppArmor profiles.  
*Citations: [2,6]*

### Runtime Detection
Deploy classifiers or anomaly detectors on prompt/tool‑call streams (see ClawGuard runtime framework for indirect injection detection).  
*Citations: [3]*

### Preference‑Optimization Defenses
Fine‑tune LLMs to reject malicious prompts via reinforcement learning from human feedback (SecAlign approach).  
*Citations: [4]*

### Structured Query Defenses
Force agents to use parameterized queries or prepared statements when interacting with databases (StruQ method).  
*Citations: [5]*

### Continuous Automated Security Auditing
Run an “audit agent” that periodically checks agent configurations, permission drift, and anomalous behavior (as in the healthcare case study).  
*Citations: [6]*

## Conclusion & Call‑to‑Action

AI agent security extends zero‑trust principles: verify, enforce least privilege, monitor, and assume breach. Engineers can start today by:

1. Enforcing per‑agent workload identities  
2. Sandboxing agent runtimes  
3. Implementing egress allow‑lists  
4. Adding prompt‑integrity wrappers  
5. Logging all tool interactions  

Continuous red‑team/blue‑team exercises and automated audit agents keep defenses current as threats evolve.

Docker's AuthZ middleware is supposed to be the last line of defense - the plugin that decides whether a container operation is allowed. CVE-2026-34040, disclosed by Cyera Research in April 2026, showed that a single padded HTTP request could make every AuthZ plugin in the ecosystem invisible.

The vulnerability class had existed since Docker Engine 1.10 - February 2016. Ten years.

## How the bypass worked

The attack is disarmingly simple. Docker Engine's AuthZ middleware inspects request bodies before allowing container operations. But request bodies larger than 1 megabyte are silently dropped before they reach the AuthZ plugins. The Docker daemon still processes the request normally.

That's the entire bug. A 1MB+ padded HTTP request bypasses authorization. The AuthZ plugin never sees it. The daemon executes the operation anyway.

The practical exploit: send a single padded HTTP request that creates a privileged container with host root access. No authentication bypass. No credential theft. Just a request that's too big for the security control to see.

## Who was affected

Every environment using AuthZ plugins - which, in a properly configured production Docker deployment, is most of them. The affected plugins include:

- **Open Policy Agent (OPA)** - the most common policy engine for container authorization
- **Prisma Cloud** - enterprise container security
- **Casbin** - open-source authorization
- **Custom AuthZ plugins** - any organization that built their own authorization middleware

This is the standard recommendation for production Docker: deploy an AuthZ plugin to restrict what container operations are permitted. CVE-2026-34040 means that recommendation was providing a false sense of security for a decade.

## The inheritance problem

This vulnerability is related to - but distinct from - CVE-2024-41110 (CVSS 10.0, disclosed 2024), which used a zero-length body to achieve the same bypass. Docker patched CVE-2024-41110, but the fix was incomplete. CVE-2026-34040 uses a different mechanism (oversized body vs. empty body) to achieve the same outcome.

The pattern matters: the authz bypass isn't a single bug - it's a vulnerability class in how Docker handles request body routing to plugins. Patching one specific bypass doesn't close the class. Docker Engine 29.3.1 addresses this properly.

## The real-world impact

The vulnerability is particularly dangerous in three scenarios:

**CI/CD pipelines.** Build systems that submit Docker API requests via the daemon socket. If an attacker can influence the request body size - through a compromised build step, a malicious Dockerfile, or a supply chain attack - they can bypass AuthZ controls to create privileged containers. In a pipeline that's supposed to run untrusted code, this is the difference between "contained breach" and "full host compromise."

**Multi-tenant container platforms.** Environments where multiple teams or customers share a Docker daemon, with AuthZ plugins enforcing isolation between tenants. The bypass means any tenant can escape their authorization boundary. Shared Docker infrastructure without user namespaces is especially exposed.

**Environments using AuthZ as the primary control.** Organizations that deployed an AuthZ plugin and considered authorization handled. The plugin was the control - and it was invisible to oversized requests.

## What to do

### Patch immediately

Docker Engine 29.3.1 addresses CVE-2026-34040. This is not a "patch when convenient" vulnerability - it's a complete bypass of a primary security control.

```bash
# Check your version
docker version

# Update (Debian/Ubuntu)
sudo apt update && sudo apt install docker-ce docker-ce-cli containerd.io

# Update (RHEL/CentOS)
sudo yum update docker-ce docker-ce-cli containerd.io
```

### Don't rely on AuthZ alone

This is the structural lesson. AuthZ plugins are a valuable layer, but they're a single point of failure in the authorization chain. The container security stack needs defense in depth:

**User Namespaces.** Kubernetes 1.36 (released April 2026) graduated User Namespaces to GA. Rootless containers - pods that run without real root on the host - are now a stable, supported configuration. Even if an AuthZ bypass creates a privileged container, user namespaces limit what that privilege means on the host. The container's "root" is a mapped UID with no real host privileges.

**Seccomp profiles.** Default seccomp profiles restrict the system calls a container can make. Even a root-privileged container can't mount the host filesystem or load kernel modules if the seccomp profile blocks those syscalls.

**AppArmor/SELinux.** Mandatory access controls add another layer. A container running as root with a restrictive AppArmor profile can't escape the profile's constraints regardless of its nominal privilege level.

**Read-only root filesystems.** Containers that can't write to their own filesystem can't persist payloads or modify binaries. This is a simple control that dramatically reduces post-exploitation options.

### Audit your AuthZ plugins

Check whether your AuthZ plugins are updated. Some plugins may have their own mitigations or configuration changes that reduce exposure. OPA's Docker authorization policy, for example, can be updated to reject oversized request bodies at the policy level - though this is a workaround, not a fix.

### Monitor for exploitation

The exploit leaves traces. Docker daemon logs record container creation events. Look for:

- Privileged containers created by unexpected callers
- Container creation requests with unusually large request bodies
- API calls that bypass the expected authorization plugin audit trail

## The container security stack is shifting

CVE-2026-34040 isn't just a Docker bug - it's evidence that the container security model needs more layers. AuthZ plugins were designed as the authorization gate, but they're only as reliable as the request routing that feeds them.

The combination of K8s 1.36 User Namespaces (GA), Docker CVE-2026-34040 (AuthZ bypass), and the broader shift toward rootless containers points in one direction: the era of "deploy a plugin and consider authorization handled" is over. Container security needs the same defense-in-depth approach that network security learned years ago. No single control is sufficient. Every layer assumes the others might fail.

Patch Docker. Enable user namespaces. Layer your controls. The vulnerability existed for a decade because the assumption was that AuthZ plugins were the boundary. They're not. They're one layer - and that layer just had a hole in it.
