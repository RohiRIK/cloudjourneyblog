"Human in the loop" is often used as a comfort phrase. It can mean anything from a person seeing a dashboard after an action has happened to a named approver authorizing one specific change before it is executed.

Those are not equivalent controls.

For an AI agent that can call tools, create tickets, change cloud resources, publish content, send messages, touch tenant data, or initiate money movement, a human approval gate needs to be a real authorization boundary. It must be understandable after the fact, not just present in a demo.

NIST's AI Risk Management Framework calls for documented, assessed, and managed processes for human oversight, along with ongoing monitoring and the ability to modify, intervene in, or shut down systems that deviate from expected behavior.[5] OWASP's AI Agent Security Cheat Sheet takes the operational version further: fail closed if risk classification, approval validation, policy lookup, or audit logging fails.[6]

That gives us a practical design target.

## First, define what the agent may do alone

A useful agent policy does not start with an approval screen. It starts with action classes.

| Action class | Examples | Default behavior |
|---|---|---|
| Read-only | Search, inspect logs, summarize files | Allow with logging |
| Reversible local work | Create a draft, run a test, stage a patch | Allow within bounded scope |
| External communication | Send email, publish a post, create a public issue | Require explicit approval |
| Privileged or consequential write | Change a tenant, deploy, delete, pay, trade, submit a form | Require explicit approval and stronger evidence |

The exact categories will differ by organization. The important thing is that the boundary is defined before the agent is asked to act. If the tool cannot classify an action, it should not guess that it is safe.

## An approval must bind to a specific action

A weak approval looks like this:

> "Approve the agent to continue?"

A useful approval includes a reviewable payload:

- **what** will change or be sent
- **where** it will happen: tenant, repository, environment, recipient, account, or destination
- **why** the agent proposes it
- **inputs and evidence** used to reach the recommendation
- **expected impact** and rollback path
- **identity of the approver**
- **expiry** and a unique action or request ID

The execution layer must verify that the approved payload still matches the action it is about to perform. If an agent requests approval for a draft and then changes the recipient list, parameters, destination, or diff, the old approval is no longer valid.

This is the difference between a workflow checkpoint and an authorization token.

## Separate proposing from approving

A reviewer should not approve their own recommendation merely because an interface asks them to click a button. For sensitive changes, use a separation-of-duties rule:

- the agent can propose
- an authorized human can approve or reject
- a different control plane validates the approval token and policy
- the execution worker performs only the approved action

NIST emphasizes accountability mechanisms, documented risks, and clearly differentiated human roles and responsibilities for AI oversight.[5] In practice, that means the approval decision belongs in a durable system record, not only in a conversational transcript.

## Capture the evidence, not just the outcome

The audit record should make an incident review possible without reconstructing the entire conversation from memory. At minimum, capture:

```text
request_id
agent and version
initiator identity
proposed action and normalized parameters
risk class and policy decision
evidence references or immutable hashes
approver identity, decision, timestamp, and expiry
execution identity, start/end timestamps, and result
rollback reference or failure reason
```

Sensitive content should be minimized or redacted. Auditability does not mean storing every secret, prompt, or customer record forever. It means retaining enough trustworthy metadata to explain the decision and prove that the action matched the approved request.

## Design for failure and interruption

Approval workflows fail in boring ways: a browser tab times out, a policy service is unavailable, a token is reused, a worker retries after a partial failure, or an approver sees stale information.

A robust gate has explicit answers:

- Can the approval be reused? Usually no; bind it to one request and expiry.
- What happens if logging is down? Fail closed for consequential actions.[6]
- What happens if execution differs from the approved plan? Stop and require a new approval.
- Can an authorized human halt the agent? Yes, with a durable kill switch and a recorded reason.
- What is the rollback path? Define it before the action becomes available.

NIST treats ongoing monitoring, periodic review, and human intervention as part of managing AI-system risk, not as optional operational polish.[5]

## Do not confuse approval with safety

Approval is one control in a layered design. It does not replace least-privilege credentials, destination allowlists, sandboxing, input validation, rate limits, or independent review.

The strongest pattern is simple:

1. Limit what the agent can attempt.
2. Require a typed policy decision for consequential work.
3. Show a human the exact action and evidence.
4. Bind approval to the immutable action request.
5. Execute through a separate, least-privileged worker.
6. Record the result and keep a way to stop or reverse it.

That makes human oversight operational instead of ceremonial. The result is not an agent that never acts; it is an agent whose real-world actions can be authorized, explained, and trusted.
