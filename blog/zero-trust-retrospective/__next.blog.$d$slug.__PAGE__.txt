I run Hermes Agent as my primary AI assistant. It's open-source, provider-agnostic, and runs in my terminal with full system access. The problem: one agent trying to do everything — security investigations, code review, job search, DevOps, content writing, research — ends up doing none of them well. Context bleeds between tasks. A security investigation session pollutes the context for code review. Job search skills load into infrastructure work.

The fix was Hermes's multi-profile system. One installation, nine independent agent profiles, each scoped to a specific domain. Here's what I built and why it works.

## Why multi-profile matters

A single Hermes instance with everything loaded hits context limits fast. Skills pile up. MCP servers compete for tool slots. Memory from one domain contaminates another. The profile system solves this by giving each domain its own complete isolated environment — config, identity, sessions, skills, memory, cron jobs, and credentials.

Think of it like user accounts on a shared machine. Each profile gets its own home directory under `~/.hermes/profiles/<name>/`, and nothing leaks between them.

## The nine profiles

Here's the full roster and what each one does:

**Bob** — Cloud Security Engineer. Investigates Microsoft 365 tenants through Entra ID, Intune, and Exchange Online MCP servers. Correlates identity and device data to catch security issues. Read-only by default.

**Ethan** — Job Search Assistant. Finds, evaluates, and tracks job applications. Manages CV optimization and career strategy for cloud security roles.

**Gabriel** — Cloud Security Investigator. Similar to Bob but focused on M365/Azure/Intune security investigations with a read-only stance. Handles incident response and compliance checks.

**Felix** — DevOps and Infrastructure Engineer. Manages Docker Swarm, CI/CD pipelines, IaC, monitoring, and workflow automation. Has n8n MCP integration for workflow orchestration.

**Max** — Code Reviewer and Quality Engineer. Finds real bugs, not style nits. Security > correctness > performance > style.

**Ella** — Content Writer and Technical Blogger. Writes blog posts, documentation, tutorials, and social media content. Direct, practical voice.

**Leo** — Research and Knowledge Agent. Deep research, paper analysis, competitive intelligence. Goes wide first, then deep.

**Sam** — Homelab and Smart Home Manager. Docker Swarm service health, IoT device status, network monitoring, backup verification, smart home automation.

**Iris** — Documentation and Knowledge Manager. Project documentation, ADRs, runbooks, contributor guides, knowledge base maintenance.

Each profile has a `SOUL.md` file that defines its identity, focus, and behavioral constraints. Bob is read-only. Max finds bugs. Ella writes clearly and skips fluff. These aren't just names — they're scoped identities that shape how the agent approaches every task.

## How profile isolation works

Each profile lives in its own directory under `~/.hermes/profiles/<name>/` with seven isolated dimensions:

**1. Configuration (`config.yaml`)** — Model, provider, toolsets, terminal backend, agent behavior. Felix uses a local terminal pointed at the homelab dashboard directory. Gabriel points at the security engineering project.

**2. Identity (`SOUL.md`)** — The agent's personality, focus areas, and behavioral rules. Each profile reads only its own SOUL.md.

**3. Sessions (`sessions/` + `state.db`)** — Conversation history and FTS5 search index. Bob's security investigations never appear in Ella's content writing sessions.

**4. Skills (`skills/`)** — Domain-specific procedural memory. Felix has Docker Swarm and CI/CD skills. Gabriel has cloud security investigation skills. These don't cross-pollinate.

**5. Memory (`memories/`)** — Persistent cross-session memory. Each profile learns independently. Max remembers code patterns from past reviews. Leo remembers research findings.

**6. Cron jobs (`cron/`)** — Scheduled tasks. Each profile can have its own recurring jobs without interference.

**7. Credentials (`.env`)** — API keys and secrets. Each profile gets its own credential set. Bob has Entra ID app registration secrets. Felix has n8n API keys. No credential sharing between profiles.

Here's what the directory structure looks like:

```
~/.hermes/profiles/
├── bob-the-sec-engineer/
│   ├── config.yaml
│   ├── SOUL.md
│   ├── .env
│   ├── sessions/
│   ├── skills/
│   ├── memories/
│   ├── cron/
│   └── mcp-servers/
├── felix/
│   ├── config.yaml
│   ├── SOUL.md
│   ├── .env
│   ├── sessions/
│   ├── skills/
│   ├── memories/
│   └── cron/
└── ... (7 more profiles)
```

## MCP server integration

The real power comes when profiles get their own MCP (Model Context Protocol) servers. MCP servers expose external tools to the agent — APIs, databases, services — as first-class callable tools.

**Felix + n8n:** Felix's config includes an n8n MCP server that gives it direct access to workflow orchestration:

```yaml
# ~/.hermes/profiles/felix/config.yaml
mcp_servers:
  n8n:
    command: "npx"
    args:
      - "-y"
      - "n8n-mcp"
    env:
      N8N_API_URL: "http://localhost:5678"
      N8N_API_KEY: "your-api-key-here"
    timeout: 120
```

With this configured, Felix can create, trigger, and manage n8n workflows directly. No manual API calls, no curl wrappers — the agent treats workflow automation as a native capability.

**Bob + Microsoft Graph MCP:** Bob has three MCP servers for Microsoft Graph — Entra ID, Intune, and Exchange Online. These give Bob read-only access to identity data, device compliance, and mail/calendar across the tenant:

```bash
# Bob's MCP servers live in their own repo
~/.hermes/profiles/bob-the-sec-engineer/mcp-servers/
├── entra_id_mcp/
├── intune_mcp/
├── exchange_online_mcp/
└── gateway_mcp/
```

Each MCP server has its own risk classification system. Read operations are unrestricted. Write operations require explicit opt-in via environment variables. The guardrails are baked in at the server level, not bolted on.

## Switching between profiles

Usage is straightforward:

```bash
# List all profiles
hermes profile list

# Use a specific profile
hermes -p felix

# Set a sticky default
hermes profile use felix

# Create a new profile (cloned from default)
hermes profile create new-agent --clone
```

In practice, I alias them in my shell:

```bash
alias bob="hermes -p bob-the-sec-engineer"
alias felix="hermes -p felix"
alias ella="hermes -p ella"
alias max="hermes -p max"
```

`bob` launches a security investigation. `felix` manages infrastructure. `ella` writes content. Each starts fresh with only its relevant context loaded.

## What changed in my daily workflow

Before profiles: one Hermes session, constantly switching context, skills loading and unloading, memory mixing between domains. A security investigation would surface job search memories. Code review would load DevOps skills.

After profiles: each domain has its own clean context. I open a terminal, pick the right profile, and everything it needs is already loaded. No context pollution. No skill conflicts. Memory stays domain-specific.

The practical impact:

- **Faster startup** — fewer skills and tools to load per profile
- **Cleaner context** — no irrelevant memories or session history
- **Better focus** — each profile's SOUL.md constrains behavior to its domain
- **Secure isolation** — credentials don't leak between profiles
- **Composable MCP** — each profile connects only to the services it needs

The initial setup took about an hour for all nine profiles. Most of that was writing SOUL.md files and configuring MCP servers. The ROI has been significant — I'm spending less time fighting context and more time actually doing the work.

Your users have personal Gmail accounts open on their work machines. They're checking personal email alongside Google Workspace. They're sharing work documents from personal Drive. IT has no visibility, no DLP, no audit trail.

This is the shadow IT problem. You can't just block personal Gmail at the network level without breaking something. But you can make it unusable for work purposes — and that's what this post covers.

## The Problem: Shadow IT in Google Workspace

Every organization has it: users who default to personal accounts for convenience. Personal Gmail on work devices. Personal Drive for sharing. Personal Calendar for everything.

The risks:
- **No DLP** — Company data leaves to personal accounts with no controls
- **No audit trail** — You can't investigate a data leak if you don't know it happened
- **No lifecycle** — When they leave, access to work data persists in their personal account
- **Compliance risk** — Often noncompliant with internal policy and regulated data-handling requirements

The goal: make personal Gmail unusable for work purposes without breaking legitimate personal use on personal devices.

## How CASB Fits In

CASB (Cloud Access Security Broker) sits between your users and cloud services, providing:
- **Visibility** — What cloud apps are being used?
- **Data protection** — DLP policies applied to cloud traffic
- **Threat protection** — Anomaly detection for cloud usage
- **Access control** — Block or restrict based on context

Google Workspace integrates with CASB via API, not inline proxy. Google explicitly recommends API/offline CASB patterns over inline proxies — inline CASBs exist but aren't the preferred path. For most orgs, Google-native controls (DLP, Reports API, App Access Management) cover much of what you need before considering third-party CASB.

### Shadow IT Discovery

Before you can block, you need to know what you're dealing with. The CASB (or Google Workspace audit logs) reveals:

- **OAuth token inventory** — Which third-party apps have user-authorized access to their Google data
- **Login activity** — Where are users authenticating from?
- **Drive sharing** — What's being shared externally?
- **App usage** — Which apps are accessing Google Workspace data?

In Google Workspace Admin console, go to Security > API controls > Access management. Review OAuth app entries — check ownership (Google-owned/internal/third-party), requested scopes, and user count. The CASB dashboard often surfaces this more visually.

Apps are categorized as **Trusted** (full access), **Limited** (specific Google data only), **Blocked** (no access), or the default for unconfigured apps. Mark unknown third-party apps as Blocked after reviewing scope and ownership.

## The Migration Strategy

### Phase 1: Discover and Categorize

List every external app accessing your users' Google data. Categorize:
- **Approved** — IT-sanctioned, security reviewed
- **Tolerated** — Not ideal but not blocked yet
- **Blocked** — Shadow IT, must go

The CASB dashboard usually provides this. If not, export audit logs and pivot in Excel.

### Phase 2: Offer a Better Alternative

Users go to personal Gmail because the sanctioned option isn't convenient. Fix that:

- **Google Workspace** — If you don't have it, get it. Every user gets company @company.com account.
- **Shared drives** — Centralize file storage so personal Drive isn't needed
- **SSO** — Single sign-on from Entra ID to Google Workspace removes the password burden

### Phase 3: Enforce with Policy

Now block. The enforcement stack, in order of impact:

**1. Block personal Google accounts** — This is what actually makes personal Gmail unusable on managed devices. Configure via proxy: `X-GoogApps-Allowed-Domains: yourdomain.com`, or in Google Admin console > Security > Managed browser > Restrict sign-in to managed accounts. This stops users from adding their personal @gmail.com account to Chrome or signing into personal Gmail on managed machines.

**2. App Access Control** — In Security > API controls > Access management, configure apps as Trusted / Limited / Specific Google data / Blocked. This controls OAuth grants, not browser access. Set default to Blocked for unconfigured apps if you want zero tolerance.

**3. Context-Aware Access** — Verify managed device before granting access to Workspace apps. Requires Endpoint Verification on desktop; mobile uses Google endpoint management (Intune, Jamf, etc.) for device signals.

### Phase 4: Data Migration

For users with existing personal Gmail data that needs to come over:

1. **Data import** — Admin imports personal Gmail to corporate account via Security > Data export and management > Data migration. Requires user authorization — they authorize their personal Gmail access. This isn't the "Google Workspace Migrate" tool (that's for Exchange migrations).
2. **Takeout** — User exports personal Drive, admin migrates to Shared Drive
3. **Calendar migration** — User exports from personal calendar, imports to corporate or shares calendar with corporate account

This takes time. Give users 30 days to migrate, then enforce.

## The Enforcement Checklist

| Control | Implementation | Effect |
|---|---|---|
| Consumer account block | X-GoogApps-Allowed-Domains header or managed browser sign-in restriction | Personal Gmail can't sign in on managed devices |
| App Access Control | Set apps to Trusted / Limited / Blocked; default to Blocked for unconfigured | No unapproved OAuth apps |
| Context-Aware Access | Require managed device (desktop: Endpoint Verification; mobile: endpoint management) | Unmanaged devices blocked |
| Drive external sharing | Allowlist or trust rules for external sharing | No uncontrolled file sharing |
| SSO | Entra ID to Google Workspace | One identity, one credential |

**CAA rollout tip:** Start in **monitor mode** first. Block only after verifying compliant devices sync Endpoint Verification — Google docs warn that sync delays can incorrectly block compliant desktops.

## What Actually Breaks First

In practice, this enforcement breaks these workflows:

1. **User's personal phone** — They can't check corporate email on their personal Android/iOS without management installed. Solution: offer MDM enrollment or accept the limitation.

2. **Third-party tools** — Users who authorized random SaaS apps lose access. Solution: pre-approve the most common ones (Zoom, Slack, etc.).

3. **Contractors** — External users without managed devices. Solution: dedicated contractor accounts with limited access, or accept unmanaged access with increased monitoring.

4. **Endpoint Verification sync delays** — Compliant desktops get blocked before they sync device status. Google's docs explicitly warn about this. Run in monitor mode first.

5. **OAuth restrictions break integrations fast** — Zoom, Slack, calendaring add-ons, scanners, backup tools — all need explicit app access configuration or users lose functionality.

6. **Delegated mailbox access** — Consumer account blocking with `X-GoogApps-Allowed-Domains` can break delegated mailbox access if the delegate's domain isn't in allowed headers.

## The Takeaway

You can't uninvent personal Gmail. Your users will always have personal accounts. What you can do is make it operationally useless for work:

- DLP policies block data exfiltration
- Context-Aware Access restricts access to managed devices
- SSO removes the password management burden
- Structured migration moves existing data to corporate

The goal isn't to punish users who use personal accounts.
