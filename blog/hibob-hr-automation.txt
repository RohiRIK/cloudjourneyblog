Docker's AuthZ middleware is supposed to be the last line of defense - the plugin that decides whether a container operation is allowed. CVE-2026-34040, disclosed by Cyera Research in April 2026, showed that a single padded HTTP request could make every AuthZ plugin in the ecosystem invisible.

The vulnerability class had existed since Docker Engine 1.10 - February 2016. Ten years.

## How the bypass worked

The attack is disarmingly simple. Docker Engine's AuthZ middleware inspects request bodies before allowing container operations. But request bodies larger than 1 megabyte are silently dropped before they reach the AuthZ plugins. The Docker daemon still processes the request normally.

That's the entire bug. A 1MB+ padded HTTP request bypasses authorization. The AuthZ plugin never sees it. The daemon executes the operation anyway.

The practical exploit: send a single padded HTTP request that creates a privileged container with host root access. No authentication bypass. No credential theft. Just a request that's too big for the security control to see.

## Who was affected

Every environment using AuthZ plugins - which, in a properly configured production Docker deployment, is most of them. The affected plugins include:

- **Open Policy Agent (OPA)** - the most common policy engine for container authorization
- **Prisma Cloud** - enterprise container security
- **Casbin** - open-source authorization
- **Custom AuthZ plugins** - any organization that built their own authorization middleware

This is the standard recommendation for production Docker: deploy an AuthZ plugin to restrict what container operations are permitted. CVE-2026-34040 means that recommendation was providing a false sense of security for a decade.

## The inheritance problem

This vulnerability is related to - but distinct from - CVE-2024-41110 (CVSS 10.0, disclosed 2024), which used a zero-length body to achieve the same bypass. Docker patched CVE-2024-41110, but the fix was incomplete. CVE-2026-34040 uses a different mechanism (oversized body vs. empty body) to achieve the same outcome.

The pattern matters: the authz bypass isn't a single bug - it's a vulnerability class in how Docker handles request body routing to plugins. Patching one specific bypass doesn't close the class. Docker Engine 29.3.1 addresses this properly.

## The real-world impact

The vulnerability is particularly dangerous in three scenarios:

**CI/CD pipelines.** Build systems that submit Docker API requests via the daemon socket. If an attacker can influence the request body size - through a compromised build step, a malicious Dockerfile, or a supply chain attack - they can bypass AuthZ controls to create privileged containers. In a pipeline that's supposed to run untrusted code, this is the difference between "contained breach" and "full host compromise."

**Multi-tenant container platforms.** Environments where multiple teams or customers share a Docker daemon, with AuthZ plugins enforcing isolation between tenants. The bypass means any tenant can escape their authorization boundary. Shared Docker infrastructure without user namespaces is especially exposed.

**Environments using AuthZ as the primary control.** Organizations that deployed an AuthZ plugin and considered authorization handled. The plugin was the control - and it was invisible to oversized requests.

## What to do

### Patch immediately

Docker Engine 29.3.1 addresses CVE-2026-34040. This is not a "patch when convenient" vulnerability - it's a complete bypass of a primary security control.

```bash
# Check your version
docker version

# Update (Debian/Ubuntu)
sudo apt update && sudo apt install docker-ce docker-ce-cli containerd.io

# Update (RHEL/CentOS)
sudo yum update docker-ce docker-ce-cli containerd.io
```

### Don't rely on AuthZ alone

This is the structural lesson. AuthZ plugins are a valuable layer, but they're a single point of failure in the authorization chain. The container security stack needs defense in depth:

**User Namespaces.** Kubernetes 1.36 (released April 2026) graduated User Namespaces to GA. Rootless containers - pods that run without real root on the host - are now a stable, supported configuration. Even if an AuthZ bypass creates a privileged container, user namespaces limit what that privilege means on the host. The container's "root" is a mapped UID with no real host privileges.

**Seccomp profiles.** Default seccomp profiles restrict the system calls a container can make. Even a root-privileged container can't mount the host filesystem or load kernel modules if the seccomp profile blocks those syscalls.

**AppArmor/SELinux.** Mandatory access controls add another layer. A container running as root with a restrictive AppArmor profile can't escape the profile's constraints regardless of its nominal privilege level.

**Read-only root filesystems.** Containers that can't write to their own filesystem can't persist payloads or modify binaries. This is a simple control that dramatically reduces post-exploitation options.

### Audit your AuthZ plugins

Check whether your AuthZ plugins are updated. Some plugins may have their own mitigations or configuration changes that reduce exposure. OPA's Docker authorization policy, for example, can be updated to reject oversized request bodies at the policy level - though this is a workaround, not a fix.

### Monitor for exploitation

The exploit leaves traces. Docker daemon logs record container creation events. Look for:

- Privileged containers created by unexpected callers
- Container creation requests with unusually large request bodies
- API calls that bypass the expected authorization plugin audit trail

## The container security stack is shifting

CVE-2026-34040 isn't just a Docker bug - it's evidence that the container security model needs more layers. AuthZ plugins were designed as the authorization gate, but they're only as reliable as the request routing that feeds them.

The combination of K8s 1.36 User Namespaces (GA), Docker CVE-2026-34040 (AuthZ bypass), and the broader shift toward rootless containers points in one direction: the era of "deploy a plugin and consider authorization handled" is over. Container security needs the same defense-in-depth approach that network security learned years ago. No single control is sufficient. Every layer assumes the others might fail.

Patch Docker. Enable user namespaces. Layer your controls. The vulnerability existed for a decade because the assumption was that AuthZ plugins were the boundary. They're not. They're one layer - and that layer just had a hole in it.

SMS MFA is on its way out. Not gradually, not optionally - Microsoft is retiring native telecom delivery for SMS and voice authentication on February 1, 2027, and passkeys are becoming the default authentication method in Entra ID starting September 1, 2026.

If you're reading this and your environment still relies on SMS as a primary or fallback second factor, the clock is already ticking. This isn't a recommendation - it's a deprecation with a hard date.

## What changed and why it matters

On July 13, 2026, Microsoft published the announcement: passkeys (FIDO2/phishing-resistant) will be the default authentication method in Entra ID. The rollout begins September 1, 2026. Users currently enabled for SMS/voice will be auto-enabled for passkeys.

Then on February 1, 2027, native SMS and voice delivery is retired. Organizations that still need SMS will have to contract third-party telecom partners through the Microsoft Security Store (partners announced September 18, 2026).

The driver isn't convenience - it's threat reality. AI-powered phishing campaigns now achieve click-through rates up to 54%, compared to roughly 12% for traditional phishing. Adversary-in-the-middle proxy attacks make SMS and push-based MFA fundamentally vulnerable. Passkeys bind the authentication ceremony to the legitimate origin cryptographically. There's nothing to intercept.

Microsoft's own Secure Future Initiative progress report (July 10, 2026) puts this in context: 99.97% of user/device pairs at Microsoft are now protected by phishing-resistant MFA. They're not just recommending it - they've deployed it at scale internally and are pushing the rest of the ecosystem to follow.

## The timeline

| Date | What happens |
|------|-------------|
| July 13, 2026 | Announcement published |
| September 1, 2026 | Rollout begins - SMS/voice users auto-enabled for passkeys |
| September 18, 2026 | Supported third-party telecom providers announced |
| February 1, 2027 | Native SMS/voice retired |
| September 7, 2026 | SSPR accepts only registered authentication methods (no more contact details as MFA) |

The September SSPR change is easy to miss. Self-service password reset will stop accepting unregistered email/phone as authentication methods. If your users registered a personal Gmail or a phone number they no longer have access to, they'll be locked out of SSPR. Verify registration state before September 7.

## What you need to do now

### Phase 1 - Audit your current state (July-August 2026)

Before you migrate anything, know what you have:

1. **Inventory authentication methods per user.** In the Entra admin center, go to Users > Authentication methods. Export the report. Identify every user with SMS or voice as their only registered method.

2. **Check SSPR registration.** Under Password reset > Authentication methods, verify what users have registered. Flag anyone with only a phone number or email as their registered method - they'll need to add a passkey before September 7.

3. **Review Conditional Access policies.** Identify any policies that rely on "Require MFA" without specifying authentication strength. These will continue to work after February 2027 but won't enforce phishing-resistant methods. Start upgrading them to reference Authentication Strengths.

4. **Audit service accounts.** Service accounts with interactive sign-ins using SMS or phone-based MFA are a blocking issue. These need certificate-based authentication or managed identity - they can't use passkeys.

### Phase 2 - Deploy passkey infrastructure (August-September 2026)

1. **Enable the passkey authentication method.** In Entra > Protection > Authentication methods, ensure FIDO2 (Security Keys) and Microsoft Authenticator (for passkey support) are enabled.

2. **Create registration campaigns.** Use Entra's built-in registration campaign feature (now GA for passkeys) to prompt users during sign-in. The campaign shows a banner directing users to register a passkey. Target users who don't yet have a phishing-resistant method.

3. **Deploy Windows Hello for Business.** For managed Windows devices, WHfB is the lowest-friction path. Users authenticate with biometric or PIN - it's already the login experience, just backed by a FIDO2 credential bound to the device. Verify Intune compliance policies and Hello provisioning policies are deployed.

4. **Deploy Platform SSO for macOS.** For Mac users, Platform SSO uses the Secure Enclave to generate a hardware-bound key that qualifies as phishing-resistant under Authentication Strengths. Requires Intune MDM enrollment and macOS 13+.

5. **Issue FIDO2 hardware keys for edge cases.** Shared workstations, kiosk scenarios, privileged users on multiple devices, and Linux workstations all need hardware keys. YubiKey 5 series or equivalent.

### Phase 3 - Migrate and enforce (September 2026-January 2027)

1. **Enroll in batches.** Don't enforce for everyone simultaneously. Create a security group (`sg-passkey-enrolled`), deploy a phishing-resistant Authentication Strength policy scoped to that group, and add users as they register.

2. **Upgrade Conditional Access policies.** Replace "Require MFA" with explicit Authentication Strength references. Phishing-Resistant MFA for privileged roles and sensitive apps. Passwordless MFA as a broader baseline. Keep existing MFA policies as a safety net.

3. **Monitor sign-in logs.** Filter for "Report-only: Would have failed" before enforcing. Identify users who would be blocked and help them register before the policy applies.

4. **Cut SMS/voice before February 2027.** Don't wait for Microsoft to retire it. If you've completed passkey enrollment for your user population, disable SMS/voice in your authentication methods policy. The fewer users on a deprecated method, the cleaner the transition.

## Linux support

A detail that matters for heterogeneous environments: phishing-resistant MFA for Linux desktops is now available via the Microsoft identity broker. Supported on Ubuntu 24.04, 26.04, RHEL 8, 9, and 10. This means your Linux workstations can participate in the same Conditional Access policies as Windows and macOS - no exceptions needed for platform coverage.

## What about third-party telecom?

If you absolutely cannot migrate away from SMS before February 2027 - legacy systems, regulatory requirements, or environments where passkey enrollment isn't feasible for a subset of users - Microsoft will support third-party telecom partners for SMS/voice delivery. The partner list goes live September 18, 2026 via the Microsoft Security Store.

This is a stopgap, not a strategy. Third-party SMS delivery adds cost, complexity, and the same phishing vulnerabilities that drove the deprecation. Use it only for the tail cases you genuinely can't reach with passkeys.

## The bigger picture

This isn't just an MFA method swap. It's Microsoft aligning the entire Entra ID ecosystem around phishing-resistant authentication as the baseline. The Conditional Access policy changes in July 2026 (CA policies now apply during Windows Hello and Platform SSO registration), the September 7 SSPR tightening, and the February 2027 SMS retirement are all parts of the same trajectory.

Environments that delay will face a forced migration with a compressed timeline. Environments that start now have six months to enroll users, test policies, and enforce gradually - which is the only way to do this without locking people out.

The passkey default isn't coming. It's already here. The question is whether you'll migrate on your terms or on Microsoft's timeline.
