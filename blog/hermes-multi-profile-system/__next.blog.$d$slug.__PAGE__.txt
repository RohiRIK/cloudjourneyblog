Intune Autopatch automates Windows, Microsoft 365 Apps, Edge, and Teams updates to improve security and productivity. To ensure patches are correctly applied and systems remain compliant, organizations can use Intune Proactive Remediations to detect missing patches and remediate them automatically. This guide provides a verifiable, end-to-end flow for engineers to implement and validate automated patching.

## Introduction

Automated patching reduces administrative overhead and improves security posture by ensuring timely updates. Windows Autopatch manages update rings and cadence as a service, while Intune Proactive Remediations allow custom detection and remediation scripts to verify patch state and fix issues automatically.

## Prerequisites

- Licensing: Microsoft 365 Business Premium, Windows 10/11 Education A3/A5, Windows 10/11 Enterprise E3/E5 (including F3), or VDA equivalents.
- Device platform: Windows 10/11 Enterprise/Education, Windows IoT Enterprise (certain LTSC limitations apply).
- Network: Internet access to Intune, Windows Update, and Autopatch endpoints.

## Step 1: Verify Prerequisites

Confirm licenses are assigned to users or devices. Ensure devices run supported Windows editions. Validate network connectivity to required endpoints (*.manage.microsoft.com, *.update.microsoft.com, etc.).

## Step 2: Enroll Devices in Windows Autopatch

In the Microsoft Endpoint Manager admin center:
1. Navigate to Devices > Windows > Windows Autopatch > Enroll.
2. Select device groups (Entra groups) to enroll.
3. Confirm enrollment status in the Autopatch enrollment blade.

## Step 3: Configure Update Rings (if needed)

Autopatch creates default Test and Last rings. Review them via Intune > Devices > Update rings.
- Avoid assigning custom rings to Autopatch-managed devices; rely on service-managed policies.
- Adjust ring settings (deferral, grace periods) only for opt-out groups.

## Step 4: Deploy Proactive Remediation Script for Patch Verification

Create a detection script that checks for the latest quality update KB (returns exit code 0 if compliant, non-zero if action needed). Create a remediation script that triggers Windows Update or resets Windows Update components.

Example detection script (PowerShell):
```powershell
# Check for KB500xxxx (example)
$hotfix = Get-HotFix -ID KB500xxxx -ErrorAction SilentlyContinue
if ($hotfix) { exit 0 } else { exit 1 }
```

Example remediation script (PowerShell):
```powershell
# Trigger Windows Update scan and install
usoclient StartScan
usoclient StartInstall
# Alternatively, reset Windows Update components
net stop wuauserv
net stop cryptSvc
net stop bits
net stop msiserver
ren C:\Windows\SoftwareDistribution SoftwareDistribution.old
ren C:\Windows\System32\catroot2 catroot2.old
net start wuauserv
net start cryptSvc
net start bits
net start msiserver
```

Deployment steps in Intune:
1. Upload detection and remediation scripts as a script package (Intune > Devices > Scripts).
2. Assign to targeting groups (can be the same Autopatch group or Entra group).
3. Set schedule (e.g., every 8 hours) and user context (System).
4. Enable notifications for failed detections.

## Step 5: Monitor Compliance and Alerts

Monitor sources:
- Intune device compliance and update compliance reports.
- Windows Autopatch Management Status Report (tenant-wide view of eligible devices).
- Windows Autopatch Alert Report (active alerts, severity, impacted update types).

Validation checks:
- Detection scripts run on schedule to verify patch state.
- Manual verification via Get-HotFix, Get-ItemProperty for registry keys, or WSUS/ConfigMgr queries.
- Handling failed patches:
  - Detection failure triggers remediation script (e.g., retry Windows Update, reset Windows Update components).
  - If remediation fails, device marked non-compliant; admin can investigate logs (WindowsUpdate.log, SetupAPI.log).
  - Rollback options: Use Windows Update for Business uninstall policies, or deploy a script to uninstall the problematic update via wusa.exe /uninstall.
- Reporting and alerting:
  - Configure alert rules in Intune for compliance drift.
  - Use Autopatch alert email notifications or webhook integrations.
  - Export reports to Power BI or Log Analytics for trend analysis.

## Step 6: Remediate Failures and Verify Fixes

- When detection fails, remediation script runs automatically.
- Verify success by checking subsequent detection returns exit code 0.
- If persistent failure, open ticket, collect logs, consider pausing the update ring for that device group.

## Step 7: Review Reports and Adjust Policies

- Weekly: Examine Intune update compliance trends.
- Monthly: Review Autopatch reports for rollback/pause events.
- Adjust ring deferrals or exclusion groups based on observed issues.
- Update detection/remediation scripts as new KBs are released.

MediaFusion solves a critical challenge in the streaming ecosystem: how to securely authenticate users on devices with limited input capabilities. From Stremio addons on Android TV boxes to Kodi installations on Raspberry Pis, many streaming devices lack full keyboards or browsers, making traditional OAuth flows impractical. MediaFusion addresses this by implementing the OAuth 2.0 Device Authorization Grant (RFC 8628), creating a seamless authentication experience that never requires users to enter credentials on the device itself.

## What is MediaFusion?

MediaFusion is an open-source streaming platform that aggregates content from configured sources-including torrent indexers, debrid services like RealDebrid and Premiumize, metadata providers, and enhancement services-into a unified interface accessible through Stremio, Kodi, or directly in a browser. Acting as an aggregation layer, it connects to over 40 external services across six major categories, eliminating the need to juggle multiple apps or websites.

The platform's strength lies in its ability to present a unified streaming experience while handling the complexity of authentication with various backend services behind the scenes.

## The OAuth 2.0 Device Authorization Grant Explained

The OAuth 2.0 Device Authorization Grant (also known as "device flow") is specifically designed for input-constrained or browserless devices. Unlike traditional OAuth flows that require redirects or embedded browsers, device flow enables authorization through a secondary device like a smartphone or laptop.

Here's how MediaFusion implements this flow:

1. **Device Authorization Request**: When configuring a debrid service (like RealDebrid), MediaFusion's configuration UI makes a GET request to the provider's `/provider/device_code` endpoint to obtain a device code and user code.

2. **User Code Display**: The configuration interface displays the user code and instructs the user to visit a verification URL on a separate device (typically a smartphone or computer) with full input capabilities.

3. **User Authorization**: The user visits the verification URL on their secondary device, enters the user code, and grants authorization to MediaFusion.

4. **Polling for Token**: While the user authorizes, MediaFusion polls the token endpoint (`/provider/authorize`) with the device code at intervals specified by the provider (typically every 5 seconds) until authorization completes or the code expires.

5. **Token Reception**: Upon successful authorization, the token endpoint returns an access token, which MediaFusion encrypts and embeds in the manifest URL via the `secret_str` parameter for seamless addon configuration.

## Why Device Flow Provides Excellent UX for MediaFusion Users

The device flow solves the authentication dilemma for streaming addons in several key ways:

- **No Browser Required on Device**: MediaFusion runs on devices that may lack browsers or have limited input (like TV boxes or Raspberry Pi setups). The device flow eliminates the need for browser-based authentication flows on these constrained devices.

- **Secondary Device Authentication**: Users complete authorization on familiar devices with full keyboards and browsers-typically smartphones or laptops-making the process intuitive and error-free.

- **Simple Code Entry**: Instead of entering complex credentials, users only need to input a short, alphanumeric user code (typically 6-8 characters), reducing friction and errors.

- **Automatic Polling**: After displaying the user code, MediaFusion automatically handles the polling process in the background, requiring no further user interaction until authorization completes or times out.

- **URL-Based Configuration**: Encrypted credentials are embedded directly in the manifest URL, eliminating separate login steps when installing the Stremio or Kodi addon. Users simply install the addon with the pre-configured manifest URL, and it just works.

## Security Analysis: What Device Flow Protects Against

The device flow provides inherent security benefits by design:

### What It Protects Against
- **Credential Exposure**: User credentials (username/password) never enter the MediaFusion device interface, eliminating credential theft from compromised devices.
- **Limited Attack Surface**: Only the device code and user code are exposed on the limited-interface device, minimizing the attack surface.

### Security Considerations & Mitigations
While inherently more secure than alternatives like Resource Owner Password Credentials (ROPC), device flow requires attention to several considerations:

1. **User Code Brute Forcing**: RFC 8628 section 5.1 specifies that user codes must be sufficiently long and random to prevent brute-force attacks. MediaFusion relies on provider-standard implementations that typically use 8-character alphanumeric codes (62^8 ~ 218 trillion possibilities).

2. **Device Code Brute Forcing**: Similarly, device codes must be sufficiently entropic (RFC 8628 section 5.2). Providers implement these with sufficient entropy to make brute-forcing impractical.

3. **Phishing Risks**: Users must verify they're entering codes on legitimate provider verification pages. MediaFusion mitigates this by displaying the exact verification URL to visit.

4. **Polling Abuse**: Providers must implement rate limiting on token endpoints to prevent abuse from frequent polling-a standard requirement RFC 8628 section 5.4 places on authorization servers.

5. **Token Lifetime Management**: Access tokens should have appropriate expiration times, with refresh token support where applicable, limiting the window of compromise if tokens are intercepted.

6. **PKCE Considerations**: While RFC 8628 doesn't mandate PKCE for device flow, some providers implement it additionally. MediaFusion works with provider implementations as-is.

## Device Flow vs. Alternative OAuth Flows

Understanding when device flow is the right choice requires comparing it to other OAuth flows:

### Device Flow vs. Authorization Code + PKCE
- **Device Flow**: Designed for input-constrained/browserless devices; uses user code + verification URL; client polls for token
- **Auth Code + PKCE**: Requires browser/user-agent on device; uses redirect_uri; authorization server redirects back to client

### Device Flow vs. ROPC (Resource Owner Password Credentials)
- **Device Flow**: Never handles user credentials; more secure against credential theft and phishing
- **ROPC**: Requires username/password handled by client; vulnerable to phishing, keylogging, and credential theft

### When Device Flow is Appropriate
Device flow is ideal when:
- Devices lack browsers or have limited input capabilities (smart TVs, streaming sticks, gaming consoles)
- You want to avoid handling user credentials on the device
- Users have access to a secondary device for authorization
- Deploying streaming/media addons (Stremio/Kodi) where seamless configuration is paramount

## How MediaFusion Implements Device Flow Technically

Based on source code analysis, MediaFusion's implementation follows these patterns:

### Device Code Request
The configuration UI initiates the flow by calling `GET /{provider}/device_code` (found in `resources/js/config_script.js` lines 33-60), which returns:
- `device_code`: Used for polling the token endpoint
- `user_code`: The code users enter on the verification page
- `verification_uri`: The URL users should visit
- `expires_in`: Validity period (typically 5-15 minutes)
- `interval`: Polling interval in seconds (usually 5)

### Token Polling
While the user authorizes, MediaFusion POSTs to `/{provider}/authorize` with the `device_code` (lines 63-96 in config_script.js), respecting the provider-specified interval to avoid abuse.

### User Code Display
The configuration interface (`resources/html/configure.html` lines 235-242) presents the user code and instructions clearly, often with copy-to-clipboard functionality for ease of use.

### Token Storage
Upon receiving the access token, MediaFusion:
1. Encrypts it using AES via `utils/crypto.py` with a site-specific `settings.secret_key`
2. Embeds the encrypted token in the manifest URL as the `secret_str` parameter
3. This allows Stremio/Kodi addons to load configured services without additional login steps

The encryption implementation spans `utils/crypto.py` and `db/schemas.py` (lines 235-348), ensuring credentials never remain in plaintext in configurations or URLs.

## Best Practices for Users When Authorizing Devices

To maximize security when using MediaFusion's device flow:

1. **Verify the Verification URL**: Always ensure you're on the legitimate provider's website when entering user codes.
2. **Use Temporary Codes**: Treat user codes as temporary passwords-don't share them or enter them on suspicious sites.
3. **Monitor Authorized Devices**: Regularly review and revoke access for devices you no longer use via the provider's account dashboard.
4. **Understand Token Scope**: Be aware of what permissions you're granting (typically limited to accessing your debrid/storage account).
5. **Keep Recovery Options Updated**: Ensure account recovery methods are current in case you need to regain access.

## Why This Approach Represents the Future of Device Authentication

MediaFusion's implementation of OAuth 2.0 Device Flow exemplifies a broader shift in how we handle authentication for the growing ecosystem of smart devices, IoT gadgets, and media-centric hardware:

- **User-Centric Security**: By separating authentication from the device interface, we achieve both security and usability without compromise.
- **Standardized Approach**: Leveraging RFC 8628 ensures compatibility with major identity providers while benefiting from community-vetted security practices.
- **Seamless Integration**: The URL-based credential embedding creates a truly "set it and forget it" experience for addon installation and configuration.
- **Extensible Framework**: As more services adopt device flow (from Google to Azure AD), MediaFusion's modular implementation can easily integrate new providers.

For streaming enthusiasts who value both convenience and security, MediaFusion's device flow implementation demonstrates how thoughtful authentication design can make complex backend integrations disappear behind a simple, "just works" user experience-exactly what the modern streaming ecosystem needs.
