I run Hermes Agent as my primary AI assistant. It's open-source, provider-agnostic, and runs in my terminal with full system access. The problem: one agent trying to do everything — security investigations, code review, job search, DevOps, content writing, research — ends up doing none of them well. Context bleeds between tasks. A security investigation session pollutes the context for code review. Job search skills load into infrastructure work.

The fix was Hermes's multi-profile system. One installation, nine independent agent profiles, each scoped to a specific domain. Here's what I built and why it works.

## Why multi-profile matters

A single Hermes instance with everything loaded hits context limits fast. Skills pile up. MCP servers compete for tool slots. Memory from one domain contaminates another. The profile system solves this by giving each domain its own complete isolated environment — config, identity, sessions, skills, memory, cron jobs, and credentials.

Think of it like user accounts on a shared machine. Each profile gets its own home directory under `~/.hermes/profiles/<name>/`, and nothing leaks between them.

## The nine profiles

Here's the full roster and what each one does:

**Bob** — Cloud Security Engineer. Investigates Microsoft 365 tenants through Entra ID, Intune, and Exchange Online MCP servers. Correlates identity and device data to catch security issues. Read-only by default.

**Ethan** — Job Search Assistant. Finds, evaluates, and tracks job applications. Manages CV optimization and career strategy for cloud security roles.

**Gabriel** — Cloud Security Investigator. Similar to Bob but focused on M365/Azure/Intune security investigations with a read-only stance. Handles incident response and compliance checks.

**Felix** — DevOps and Infrastructure Engineer. Manages Docker Swarm, CI/CD pipelines, IaC, monitoring, and workflow automation. Has n8n MCP integration for workflow orchestration.

**Max** — Code Reviewer and Quality Engineer. Finds real bugs, not style nits. Security > correctness > performance > style.

**Ella** — Content Writer and Technical Blogger. Writes blog posts, documentation, tutorials, and social media content. Direct, practical voice.

**Leo** — Research and Knowledge Agent. Deep research, paper analysis, competitive intelligence. Goes wide first, then deep.

**Sam** — Homelab and Smart Home Manager. Docker Swarm service health, IoT device status, network monitoring, backup verification, smart home automation.

**Iris** — Documentation and Knowledge Manager. Project documentation, ADRs, runbooks, contributor guides, knowledge base maintenance.

Each profile has a `SOUL.md` file that defines its identity, focus, and behavioral constraints. Bob is read-only. Max finds bugs. Ella writes clearly and skips fluff. These aren't just names — they're scoped identities that shape how the agent approaches every task.

## How profile isolation works

Each profile lives in its own directory under `~/.hermes/profiles/<name>/` with seven isolated dimensions:

**1. Configuration (`config.yaml`)** — Model, provider, toolsets, terminal backend, agent behavior. Felix uses a local terminal pointed at the homelab dashboard directory. Gabriel points at the security engineering project.

**2. Identity (`SOUL.md`)** — The agent's personality, focus areas, and behavioral rules. Each profile reads only its own SOUL.md.

**3. Sessions (`sessions/` + `state.db`)** — Conversation history and FTS5 search index. Bob's security investigations never appear in Ella's content writing sessions.

**4. Skills (`skills/`)** — Domain-specific procedural memory. Felix has Docker Swarm and CI/CD skills. Gabriel has cloud security investigation skills. These don't cross-pollinate.

**5. Memory (`memories/`)** — Persistent cross-session memory. Each profile learns independently. Max remembers code patterns from past reviews. Leo remembers research findings.

**6. Cron jobs (`cron/`)** — Scheduled tasks. Each profile can have its own recurring jobs without interference.

**7. Credentials (`.env`)** — API keys and secrets. Each profile gets its own credential set. Bob has Entra ID app registration secrets. Felix has n8n API keys. No credential sharing between profiles.

Here's what the directory structure looks like:

```
~/.hermes/profiles/
├── bob-the-sec-engineer/
│   ├── config.yaml
│   ├── SOUL.md
│   ├── .env
│   ├── sessions/
│   ├── skills/
│   ├── memories/
│   ├── cron/
│   └── mcp-servers/
├── felix/
│   ├── config.yaml
│   ├── SOUL.md
│   ├── .env
│   ├── sessions/
│   ├── skills/
│   ├── memories/
│   └── cron/
└── ... (7 more profiles)
```

## MCP server integration

The real power comes when profiles get their own MCP (Model Context Protocol) servers. MCP servers expose external tools to the agent — APIs, databases, services — as first-class callable tools.

**Felix + n8n:** Felix's config includes an n8n MCP server that gives it direct access to workflow orchestration:

```yaml
# ~/.hermes/profiles/felix/config.yaml
mcp_servers:
  n8n:
    command: "npx"
    args:
      - "-y"
      - "n8n-mcp"
    env:
      N8N_API_URL: "http://localhost:5678"
      N8N_API_KEY: "your-api-key-here"
    timeout: 120
```

With this configured, Felix can create, trigger, and manage n8n workflows directly. No manual API calls, no curl wrappers — the agent treats workflow automation as a native capability.

**Bob + Microsoft Graph MCP:** Bob has three MCP servers for Microsoft Graph — Entra ID, Intune, and Exchange Online. These give Bob read-only access to identity data, device compliance, and mail/calendar across the tenant:

```bash
# Bob's MCP servers live in their own repo
~/.hermes/profiles/bob-the-sec-engineer/mcp-servers/
├── entra_id_mcp/
├── intune_mcp/
├── exchange_online_mcp/
└── gateway_mcp/
```

Each MCP server has its own risk classification system. Read operations are unrestricted. Write operations require explicit opt-in via environment variables. The guardrails are baked in at the server level, not bolted on.

## Switching between profiles

Usage is straightforward:

```bash
# List all profiles
hermes profile list

# Use a specific profile
hermes -p felix

# Set a sticky default
hermes profile use felix

# Create a new profile (cloned from default)
hermes profile create new-agent --clone
```

In practice, I alias them in my shell:

```bash
alias bob="hermes -p bob-the-sec-engineer"
alias felix="hermes -p felix"
alias ella="hermes -p ella"
alias max="hermes -p max"
```

`bob` launches a security investigation. `felix` manages infrastructure. `ella` writes content. Each starts fresh with only its relevant context loaded.

## What changed in my daily workflow

Before profiles: one Hermes session, constantly switching context, skills loading and unloading, memory mixing between domains. A security investigation would surface job search memories. Code review would load DevOps skills.

After profiles: each domain has its own clean context. I open a terminal, pick the right profile, and everything it needs is already loaded. No context pollution. No skill conflicts. Memory stays domain-specific.

The practical impact:

- **Faster startup** — fewer skills and tools to load per profile
- **Cleaner context** — no irrelevant memories or session history
- **Better focus** — each profile's SOUL.md constrains behavior to its domain
- **Secure isolation** — credentials don't leak between profiles
- **Composable MCP** — each profile connects only to the services it needs

The initial setup took about an hour for all nine profiles. Most of that was writing SOUL.md files and configuring MCP servers. The ROI has been significant — I'm spending less time fighting context and more time actually doing the work.

We spent three years rolling out Zero Trust at a defense technology company. 57 tasks later, here's what actually worked — and what broke in production.

## The Implementation Sequence

Zero Trust isn't a product you buy. It's a sequence of controls you enforce, in order, with each phase creating the foundation for the next.

### Phase 1: Emergency Access & Monitoring Foundation

Before touching anything else, you need:

- **Breakglass accounts** — Named emergency accounts that bypass all Conditional Access. Don't use these daily. Test them quarterly.
- **Alerting baseline** — What does normal look like? Capture login patterns, device health, app usage before you start blocking.

This is the unsexy phase that saves you when Phase 3 locks everyone out.

### Phase 2: Security Info Registration

Before enforcing MFA, users need to register authentication methods. Set this up first:
- **Auth methods policy** — Enable Microsoft Authenticator, FIDO2, Windows Hello for Business
- **Temporary Access Pass** — One-time codes for users who lose hardware keys
- **Report-only mode** — Test CA policies before enforcing

### Phase 3: Block Legacy Authentication

Legacy auth (SMTP auth, basic auth, POP/IMAP) is the attack surface. Block it:

```
Conditional Access > Assignments > Cloud apps > All apps
Conditions > Client apps > Select Exchange ActiveSync clients and Other clients
Controls > Grant > Block access
```

Block legacy auth too early and you'll break:
- Legacy application integrations
- Service accounts with password auth only
- Old MFA integrations that sit behind legacy protocols

**What broke first:** SMTP-authenticated printer scanning and IoT device integrations. Both used basic auth with no modern auth path.

### Phase 3: MFA Enforcement

Phishing-resistant MFA is the goal. FIDO2 hardware keys. But hardware keys have procurement and onboarding friction:

- Procurement: Buy 50 keys, distribute to Tier-1 roles (privileged users, admins)
- Onboarding: Users need to register in-browser with Chrome/Edge (Firefox support is spotty)
- Policy: Require phishing-resistant MFA for admin roles; offer standard MFA as fallback for general users

**What broke first:** Users who lost their hardware keys. Registration flow required a new key + backup key, and the process times out fast.

### Phase 4: Device Compliance (Intune Baselines)

Intune security baselines + Conditional Access is where device trust lives:

- **Windows baseline** — BitLocker, Windows Defender, firewall rules
- **Device compliance policy** — Require Microsoft Entra hybrid joined OR compliant device
- **MDE integration** — Device risk from Defender feeds CA decisions

**What broke first:** Microsoft Entra hybrid join fails when:
- Stale device objects in on-prem AD aren't cleaned up
- Line-of-business apps still query on-prem AD only (no cloud auth path)
- Users are co-managed (Intune + SCCM) and the policy boundary isn't clear

### Phase 5: Session Controls

Sign-in frequency and device restrictions for existing sessions:
- **Sign-in frequency** — Re-authenticate after X hours or when device state changes
- **Persistent browser** — Block to prevent session cookie replay
- **App-enforced restrictions** — Disable clipboard/file copy for unmanaged devices

### Phase 6: Risk-Based Conditional Access

Identity Protection risk signals drive dynamic policies:

- **High-risk sign-in** — Block or require MFA
- **Risky user** — Force password reset
- **Microsoft Defender for Identity** — Detect lateral movement, privilege escalation, and domain escalation attacks

**What broke first:** False positives. Risky sign-in policies flagged VPN users on corporate devices because the sign-in location didn't match.

### Phase 7: Network Segmentation (802.1X)

WiFi authentication via 802.1X (WPA2-Enterprise) is network-level Zero Trust:

- **EAP method** — EAP-TLS with certificate-based auth (vs. EAP-PEAP/MSCHAPv2)
- **Certificate lifecycle** — SCEP or PKCS certificate profile from Intune
- **Fallback** — WPA2-PSK for legacy devices that can't do 802.1X

**What broke first:** EAP negotiation failures. Root causes:
- Wrong EAP type configured on client vs. RADIUS
- Server certificate missing trusted root on client
- Server name validation mismatch (certificate SAN doesn't match RADIUS hostname)
- Expired or revoked client/server certificates

## What Actually Broke First

After three years, here's the friction ranking:

| Friction Point | Phase | Symptom |
|---|---|---|
| 802.1X EAP failures | Network | Users can't connect to WiFi; RADIUS shows method mismatch |
| Device baseline conflicts | Device | Co-managed devices have conflicting policies from SCCM and Intune |
| Legacy app breakage | Identity | LOB apps fail when legacy auth is blocked |
| False-positive risky sign-ins | Identity | VPN users flagged as risky based on location |
| Hardware key loss | MFA | Users lose keys, no backup, lockout |
| Breakglass account lockout | Foundation | Breakglass account passwords expire or are not tested |

## The Hard Lessons

1. **Don't start with blocking.** Start with alerting and monitoring. Baseline normal before you break normal.

2. **Phased enforcement, not big bang.** Each phase enables the next. Block legacy auth → enforce MFA → require device compliance → apply risk-based access.

3. **802.1X is the hardest network control.** Budget double the time for 802.1X pilot. EAP-TLS certificate validation is where it fails.

4. **Device trust requires clear ownership.** If you're co-managed (SCCM + Intune), define the boundary. We used Intune for cloud-native devices, SCCM for remaining on-prem managed.

5. **Governance is the bottleneck.** Zero Trust fails when cross-team ownership isn't clear. Identity owns CA policies. Endpoint owns device baselines. Network owns 802.1X. Security owns MDI.

## The Takeaway

Zero Trust isn't a project with an end date. It's an operational posture. The sequence matters: emergency access → security info registration → legacy block → MFA → device compliance → session controls → risk-based access → 802.1X.
